## 0. Идея и продуктовый скоуп

Календарь как полноценный раздел внутри экосистемы Контур.Толк — пятая вкладка
рядом с Чатами, Артефактами, Досками и Контактами.

### Ключевые фичи (то, ради чего всё затевается)

1. **Уведомление перед началом следующей встречи** — проактивный тост/пуш за N минут
   с кнопкой «Присоединиться», ведущей прямо в комнату Толка.
2. **Постановка встреч через LLM** — та же модель, что уже собирает ИИ-саммари, извлекает
   из протокола договорённости вида «созвонимся в четверг по биллингу» и предлагает
   готовый черновик встречи с участниками, темой и слотом.
3. **Интеграция с внешними календарями** — в первую очередь Google Calendar,
   плюс универсальный ICS-фид как запасной вариант.

### Явно вне скоупа

- Реальная запись/транскрибация встреч — берём как данные от Толка, не воспроизводим.
*(Примечание: блок «Дни рождения — кого показывать», ранее считавшийся вне скоупа по статичному макету `template_1.png`, в интерактивном прототипе `template_1.html` детально проработан и возвращён в скоуп Этапа 3).*

## Этап 2. Базовый функционал по макету — ✅ сделано

**Цель:** календарь, который реально работает — можно создавать, двигать и открывать встречи.

### 2.1 Модель данных — ✅

Сущности: `User`, `Calendar`, `Event`, `EventParticipant`, `RecurrenceRule`,
`ExternalAccount`, `Reminder`. Для хранения сущностей на данном этапе храним просто SQLite. Пользователи определяются просто по имени. Все имена уникальные. Если я начал тестировать с именем Сергей, то в следующий раз когда я введу это же имя я получу все тоже самое. Никакой авторизации и паролей сейчас не будет, просто ввод имени.

Ключевые решения, которые дешевле принять сейчас:

- Время храним в **UTC**, таймзону пользователя — отдельным полем.
- Повторяемость — по **RFC 5545 (RRULE)**, а не самописным форматом: иначе
  синхронизация с Google и ICS превратится в боль.
- Развёртка повторов в конкретные вхождения — на чтении, не в БД.
- Статус участника: `accepted / declined / tentative` — ровно как на макете
  («идёт», «не идёт», «возможно»).

### 2.2 API — ✅

```
GET    /api/events?from=&to=&calendarIds=
POST   /api/events
PATCH  /api/events/{id}          # + перенос drag&drop
DELETE /api/events/{id}
POST   /api/events/{id}/rsvp
GET    /api/calendars
PATCH  /api/calendars/{id}       # вкл/выкл галочку видимости
GET    /api/events/{id}/artifacts
```

### 2.3 UI по макету — ✅

**Шапка:** табы Календарь / Чаты / Артефакты / Доски / Контакты, счётчик непрочитанного,
кнопка «Созвониться сейчас».

**Левая панель:**

- Кнопка «Создать встречу».
- Мини-календарь месяца с навигацией и подсветкой сегодня/выбранного дня.
- «Мои календари» — цветные чекбоксы видимости (Рабочие встречи, Личное,
  Дни рождения, Задачи и дедлайны).
- «Списки участников» с счётчиками и кнопкой добавления.

**Центральная сетка:**

- Переключатель День / Неделя / Месяц / Год, кнопка «Сегодня», стрелки навигации, поиск.
- Недельная сетка 24 часа, полоса «весь день» сверху.
- **Линия текущего времени** с меткой — она же основа для фичи уведомлений.
- События: цвет по календарю, drag&drop переноса, resize границ,
  пунктирная рамка для «возможно», иконки артефактов на карточке.

**Правая панель встречи:**

- Заголовок, дата/время, признак повторяемости.
- Ссылка на видеовстречу `talk.kontur.ru/c/...` и кнопка «Присоединиться».
- **Артефакты встречи**: запись, ИИ-протокол, доска, задачи — карточки со стрелкой.
- **Участники** со статусами и цветными аватарами.

### 2.4 Фича «Уведомление перед следующей встречей» — ✅

- Настройка времени напоминания на встречу (за 5/10/15 мин).
- Клиентский планировщик + Web Notifications API.
- Тост поверх интерфейса: тема, «до начала N минут», кнопка «Присоединиться».
- Отдельно обработать случай «встреча уже идёт, вы ещё не в ней».

**Готово, когда:** на локальном стенде можно прожить рабочий день — создать встречу,
перетащить, позвать участников, получить напоминание, открыть панель артефактов.
— ✅ выполнено, приёмка пройдена на `docker compose up`.

### Что получилось

- **Вход по имени.** `POST /api/session` заводит рабочее пространство при первом входе
  и возвращает то же самое при повторном. Имя нечувствительно к регистру и краевым
  пробелам. Клиент носит идентификатор в заголовке `X-Talkaton-User` — единственное
  место, которое на этапе 6 заменит SSO.
- **Демо-неделя при первом входе:** четыре календаря с макета, три списка участников,
  восемь коллег и 17 встреч, включая всё-дневную и витринный «Штаб Платформы Данных» —
  повторяется каждую среду, с четырьмя артефактами и пятью участниками в разных статусах.
  Неделя привязана к неделе первого входа в поясе клиента, поэтому демо всегда «сегодняшнее».
- **Сетка:** день, неделя, месяц и год; полоса «весь день», линия текущего времени
  с меткой, перетаскивание и растягивание встреч, двойной щелчок по пустому месту создаёт
  встречу на этот час. Пересекающиеся встречи делят ширину колонки по дорожкам.
- **Правая панель:** дата с расшифровкой повторения, ссылка в комнату Толка, кнопка
  «Присоединиться», артефакты карточками, участники со статусами, ответ на приглашение
  и выбор времени напоминания.
- **Напоминания:** клиентский планировщик пересчитывает ближайшие встречи по тику,
  а не заводит таймер на каждую — переживает сон ноутбука и правку в соседней вкладке.
  Тост поверх интерфейса плюс системное уведомление через Web Notifications;
  случай «встреча уже идёт, вас ещё нет» обработан отдельным видом тоста.
- **Списки участников** создаются в модалке: название, поиск по людям, выбор
  чекбоксами, ошибки валидации и состояние сохранения. Инлайн-поле в левой панели,
  отправлявшее список без единого участника, убрано.
- **Горячие клавиши из прототипа:** D/W/M/Y переключают вид, T возвращает на сегодня,
  C создаёт встречу, стрелки листают период, Escape закрывает верхний слой.
  Молчат, пока фокус внутри поля ввода.
- **Тесты:** 50 на бэкенде (RRULE, развёртка вхождений, все эндпоинты через
  `WebApplicationFactory` на SQLite в памяти) и 24 на фронте. Приёмка этапа вынесена
  в `.github/scripts/smoke-stage-2.sh` и гоняется в джобе compose.

**Решения, принятые по ходу и не отражённые в изначальном плане:**

- **SQLite вместо PostgreSQL** — [ADR 0003](docs/adr/0003-sqlite-na-etape-2.md).
  Сервис `postgres` убран, стенд поднимается двумя контейнерами.
- **`RecurrenceRule` — не таблица, а разбор строки RRULE.** Правило живёт полем
  `Event.RecurrenceRule`, отдельная сущность только размножила бы состояние.
- **Перенос одного вхождения серии — строка-исключение** и параметр `scope`
  у `PATCH`/`DELETE` — [ADR 0004](docs/adr/0004-iskliucheniya-vhozhdeniy.md).
- **`Reminder` — на пару (встреча, участник)**, а не поле встречи: у каждого своё.
- **Права:** править и удалять встречу может организатор; участнику доступны
  ответ на приглашение и собственное напоминание.
- **Видимость календарей фильтруется на клиенте**, хотя `GET /api/events` умеет
  `calendarIds`: галочка должна отзываться мгновенно и без мигания сетки.
- **Запрашиваем всегда не меньше месяца** вокруг опорной даты — иначе в виде «День»
  мини-календарю нечем рисовать точки занятых дней.
- **Встречи, куда позвали снаружи, видны всегда** и галочками не скрываются:
  своего календаря для них в левой панели нет.
- Блок «Дни рождения — кого показывать» не реализован — он перечёркнут на макете.

## Этап 3. VPS, домен и эмуляция Толка

**Цель:** публичный стенд, на котором календарь живёт в декорациях настоящего Толка.

### 3.1 Инфраструктура — ✅

Стенд живёт на **https://talkaton.duckdns.org**: Ubuntu-VPS, домен DuckDNS, nginx
на хосте терминирует TLS через Let`s Encrypt и проксирует один-единственный порт
в контейнер `web` — тот сам разбирает `/api/` и уводит его в API.

Три решения разошлись с планом:

- **Отдельного `docker-compose.prod.yml` не появилось.** При слиянии compose-файлов
  списки `ports` склеиваются, а не заменяются, и второй файл дал бы конфликт за порт.
  Вместо него порты, адрес привязки, окружение и политика перезапуска стали
  переменными с прежними значениями по умолчанию; на сервере их задаёт `.env`.
- **Контейнеры слушают только `127.0.0.1`** — единственный рабочий способ убрать
  порт из внешнего доступа. Docker публикует порты правилами в цепочке `DOCKER`,
  которая обходит `INPUT`, поэтому ufw их не фильтрует ни в ту, ни в другую сторону.
- **Бэкап не `pg_dump`, а том SQLite** — следствие [ADR 0003](docs/adr/0003-sqlite-na-etape-2.md):
  `tar` по тому `sqlite-data`. По расписанию пока не поставлен.

Выкатка — задание `deploy` в CI, за `needs` на все три проверки, так что сломанный
коммит на стенд не попадёт. Ключ на сервере ограничен принудительной командой
в `authorized_keys`: что запускать, решает сервер, заданию нечего передавать,
и утёкший ключ умеет ровно одно — пересобрать стенд. Скрипт лежит вне рабочей копии,
потому что делает `git reset --hard` в ней же. Версия интерфейса подписана в левом
нижнем углу — по ней видно, доехала ли сборка, не заглядывая в логи Actions.

**Что вскрылось по дороге:** сборка шла тем SDK, который окажется на машине, а при
`LangVersion=latest` это меняет и версию языка. Под C# 14 `массив.Contains(x)`
уходит в `MemoryExtensions.Contains` по `ReadOnlySpan<T>`, в дерево выражения
попадает ref struct, и интерпретатор EF Core 8 на нём падает: тест проходил локально
и падал в CI. Закрыто `global.json` и явным `LangVersion`.

**Осталось по инфраструктуре:** бэкап по расписанию и присмотр за диском — каждая
выкатка собирает образы заново.

### 3.2 Эмуляция контура Толка (не реализовано / в очереди)

Ключевая часть этапа: нужно проверить, что календарь корректно разговаривает
с Толком, ещё не имея доступа к самому Толку. В текущем коде проекта этого сервиса
ещё нет (пока работают только локальные seed-данные в БД).

- **Mock-сервис Толка**: эмулятор внешнего API Толка, выдающий список сотрудников,
  комнаты видеовстреч (`talk.kontur.ru/c/...`), готовые саммари и артефакты — контракт сразу
  проектируется под будущее API Толка.
- **Заглушка авторизации**, повторяющая ожидаемый SSO-поток Контура.
- **Anti-Corruption Layer**: весь код взаимодействия с Толком изолируется
  за интерфейсом `ITalkGateway`. На этапе 6 меняется только реализация.
- **Вебхук-эндпоинт**: приём события «встреча завершилась, саммари готово» — триггер для LLM-фичи.

### 3.3 Интеграция с Google Calendar

- OAuth 2.0, экран согласия, хранение refresh-токенов.
- Импорт событий, двусторонняя синхронизация, `syncToken` для инкрементальных обновлений.
- Разрешение конфликтов: последняя запись побеждает, но с журналом изменений.
- Отдельно: подписка на внешний **ICS-фид** — дешёвый способ поддержать
  Outlook, Яндекс и всё остальное разом.

### 3.4 Проверка на стенде

- Прогон демо-сценария целиком, несколько пользователей одновременно.
- Проверка таймзон и переходов через полночь — классический источник багов.
- Замер: сетка недели не должна тормозить на ~200 событиях.

## Этап 4. LLM-постановка встреч (мок на фикстурах)

**Цель:** фича работает end-to-end и стабильно показывается на демо.

- Интерфейс `IMeetingExtractor`: на входе — текст саммари и контекст участников,
  на выходе — список черновиков встреч.
- Реализация `FixtureMeetingExtractor`: заранее подготовленные саммари реальных
  встреч → предсказуемые черновики. Никакой сети, демо не падает.
- Набор фикстур: 5–7 сценариев, включая пограничные («договорились созвониться,
  но без даты», «перенесли существующую встречу»).
- UI: карточка-предложение «Из встречи X: поставить созвон по биллингу в чт 14:00?»
  с кнопками «Создать» / «Изменить» / «Отклонить».
- Обязательно: **ничего не создаётся без подтверждения человека.**
  Автосоздание встреч от имени пользователя — быстрый способ потерять доверие.
- Триггер — вебхук «саммари готово» из мока Толка (этап 3.2), связанный с признаком записи/протокола встречи.

### Уточнения по предложению коллеги (Этап 8, не реализовано)

- **Визуальный маркер черновика.** На самой сетке календаря черновик — серым,
  с полупрозрачным слоем карточки и отдельной иконкой черновика, отличимой от
  обычной встречи с первого взгляда.
- **Прослеживаемость.** В описании черновика — из какого именно мероприятия и
  протокола он собран: расшифровка протокола может быть неверной, и человеку
  нужно быстро понять, откуда взялось предложение, а не только принять/отклонить вслепую.
- **Подбор слота по составу участников — самая сложная часть.** Два отдельных
  риска: (а) точно определить состав участников новой встречи — кто-то с прошлой
  встречи может быть не нужен на новой, даже если это не проговорено явно,
  просто "и так понятно"; (б) сам подбор свободного слота — можно переиспользовать
  движок `/api/availability` из Этапа 7.1, но там сегодня только визуализация
  для человека, а нужен ещё и алгоритм автовыбора конкретного слота.
- **Ручной вкл/выкл на встрече.** Кнопка «включить постановку через LLM» на самой
  встрече — не дёргать LLM всегда подряд, а только когда явно проговорено, что
  будет новая встреча. Поток: проговорили → нажали → ждём протокол → подбирается
  слот → появляется черновик.

**Готово, когда:** завершение встречи в моке приводит к появлению предложения
в календаре, и его можно принять одним кликом.

### 7.1 Грид занятости участников (free/busy) — ✅ сделано (2026-09-07)

- При выборе времени встречи (до сохранения) организатор видит визуальную сетку —
  кто из уже добавленных участников занят, а кто свободен на этот период, по данным
  внутренних и синхронизированных внешних календарей.
- Основание: флагманская фича Google Calendar (Find a time) и Microsoft Outlook
  (Scheduling Assistant); частично есть у Bitrix24 и Notion Calendar.
- Минимум: простой грид «время × участник» с цветовой заливкой занято/свободно.
- Задел на будущее (если останется время): авто-подсказка 2-3 лучших слотов.

### 7.2 Бронирование переговорок — ✅ сделано (2026-09-07)

- При создании очной/гибридной встречи — выбор переговорки из списка помещений
  с проверкой доступности на выбранное время, бронирование комнаты вместе со встречей.
- Основание: есть у Google, Bitrix24, TrueConf, Microsoft (Room Finder).
- Для хакатона реестр переговорок можно замокать, если нет реального API офиса.

### 7.3 Ротация по очереди (round-robin) — ✅ сделано (2026-09-07)

- Для встреч определённого типа (например, «консультация с любым доступным
  специалистом») можно назначить не конкретного человека, а группу — система по
  очереди распределяет входящие встречи между участниками группы.
- Основание: флагманская фича Calendly и Cal.com.
- Нужен явный список/группа сотрудников для ротации и трекинг «кто следующий по очереди».

### 7.4 Публичная страница самозаписи — ✅ сделано (2026-09-07)

- У пользователя есть личная ссылка вида «забронировать время у меня» — сторонний
  человек открывает её, видит реально свободные слоты (с учётом занятости и рабочих
  часов) и бронирует понравившийся сам, без переписки «когда вам удобно».
- Основание: есть у 5 из 8 конкурентов (Calendly, Cal.com, Bitrix24, Notion Calendar,
  Microsoft Bookings).
- После бронирования встреча создаётся автоматически у обеих сторон.

### 7.5 Резервное время до/после встречи (буфер) — ✅ сделано (2026-09-07)

- Настраиваемый буфер (например, 10 минут до и/или после), который автоматически
  резервируется и не даёт запланировать следующую встречу впритык.
- Особенно важно вместе с 7.1 (грид занятости) и 7.4 (публичная страница самозаписи).

### 7.6 Создание встречи от чужого имени (делегирование) — ✅ сделано (2026-09-07)

- Один пользователь (например, ассистент) получает право создавать и редактировать
  встречи в календаре другого пользователя (например, руководителя) от его имени —
  встреча в системе числится за руководителем, хотя фактически её завёл ассистент.
- Основание: есть у Zoom (Scheduling Privilege), Google Calendar, Calendly, TrueConf.
- Нужна модель прав доступа «делегат управляет календарём другого» и явный признак
  в данных, кто фактически создал встречу (даже если остальным участникам это не
  показывается).

### Явно НЕ входит в этот этап

По итогам конкурентного анализа осознанно отклонено (подробное обоснование — в
`../конкурентный-анализ-календаря.md`, раздел «Что осознанно НЕ берём»):

- Общий слот для нескольких хостов сразу (collective scheduling) — нишевый
  B2C/sales-паттерн, не под сценарий «два коллеги договариваются о встрече».
- Автоопределение часового пояса, приём оплаты при бронировании, связь со
  сделкой/задачей (CRM) — не релевантно для встреч сотрудников одной компании.

инфраструктуру Контура), настройка в профиле пользователя.

**8.2.2 Чаты-дровер.** Отдельная настройка (галочка) — клик по вкладке «Чаты» не
открывает отдельное окно, а выпадает из верхней навигации поверх календаря: список
диалогов, переписка, поле ответа, без потери контекста календаря. Вне скоупа
Толкатрона как отдельного демо-проекта — это, по сути, доработка самого Толка,
имеет смысл только на Этапе 6 (склейка с Толком), не раньше.

**8.2.3 Интерактивный экран задач.** Артефакт «Задачи» — не статичная карточка,
а список с чекбоксами выполнения, полем исполнителя, сроком и кнопкой «Назначить
себе». В связке с Этапом 4/5 (LLM) — не только доставать и предлагать встречи из
протокола, но и вытаскивать список задач тем же способом.

**8.2.4 Дни рождения — объединение в одну плашку.** Если в один день несколько
дней рождения — на полосе «весь день» одна плашка вместо нескольких, клик
открывает список всех именинников дня и (если технически возможно) переход в
внутренний Стафф Контура.

**8.2.5 Focus Time.** Пользователь может пометить блок времени как защищённый —
система автоматически отклоняет/помечает конфликтом любое новое приглашение,
пересекающееся с этим блоком.

**8.2.6 Speedy meetings по умолчанию.** Настройка дефолтной длительности новой
встречи — 25/50 минут вместо 30/60, чтобы между встречами оставался разрыв.
Применяется как значение по умолчанию в форме создания, не меняет уже
существующие встречи.

**8.2.7 Быстрый ввод на естественном языке.** Поле «созвон с Аней завтра в 15» →
готовый черновик события (тема, дата/время, участник). Младший брат Этапа 4 —
проще, чем разбор протокола прошедшей встречи: разбор одной строки, а не связного
текста. Может использовать тот же `IMeetingExtractor`-интерфейс с более простой
фикстурой на первое время.

**8.2.8 Рабочие часы и working location** (⚠️ статус — открытый вопрос, не решение).
Сотрудник указывает в настройках, откуда он сегодня работает (офис/дом), и в
рабочие ли часы — чтобы LLM (Этап 4) и коллеги при планировании понимали, звать
в очный формат или на видео. Коллега сам считает функцию спорной для Контура —
не беру в реализацию, пока команда не обсудит явно.

**8.2.9 Часовые пояса и мультизона** (⚠️ статус — открытый вопрос, конфликт с более
ранним решением, см. 8.1). Сотрудник задаёт свою локацию, время синхронизируется
относительно ЕКБ (настраиваемо). Требует отдельного решения команды: либо
подтвердить прошлое исключение из бэклога, либо пересмотреть его с учётом нового
предложения — не делаю этот выбор за команду.

### Явно НЕ входит в этот этап

- Чаты-дровер (8.2.2) — осознанно отложено до Этапа 6, склейки с настоящим Толком.
- Рабочие часы/working location (8.2.8) и часовые пояса/мультизона (8.2.9) —
  требуют отдельного решения команды прежде, чем брать в реализацию.

**Готово, когда:** по каждому пункту 8.2.1–8.2.9 команда явно решила — берём в
реализацию или нет, и явные пункты (8.2.1, 8.2.3, 8.2.4, 8.2.5, 8.2.6, 8.2.7)
реализованы и показываются в демо-сценарии наравне с Этапом 7.

## Порядок и риски

**Критический путь:** этап 1 → 2 → 3 → 4 → 6. Этап 5 можно делать параллельно
с 3 и 6, он не блокирует демо. **Этапы 7 и 8 — вне критического пути**: это
независимые наборы фич поверх готового Этапа 2 (Этап 7 — по итогам конкурентного
анализа, Этап 8 — по итогам сверки с предложением коллеги); можно делать
параллельно с 3–6 или после защиты базового сценария, в зависимости от
оставшегося времени — команде стоит самой решить, где их вставить в реальный
порядок работ. Часть пунктов Этапа 8 (8.2.8, 8.2.9) вообще не берутся в работу
до отдельного решения команды — см. Этап 8.

**Что важно не откладывать:**

- `ITalkGateway` как единая граница — вводим сразу на этапе 3, иначе интеграция
  на этапе 6 расползётся по всему коду.
- Хранение времени в UTC и RRULE — переделывать это позже дороже всего.
- Тёмная тема в токенах с самого начала, а не «покрасим потом».

**Основные риски:**

| Риск                                                                       | Смягчение                                                                                 |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Нет доступа к внутренним API Толка до финала | Anti-Corruption Layer + mock-сервис с самого начала                             |
| Google OAuth не успевает пройти верификацию         | Тестовый режим приложения + ICS-фид как запасной путь     |
| LLM подводит на демо                                             | Фикстуры как основной путь, реальная модель за флагом |
| Таймзоны и повторяемость съедают время       | Берём RRULE и UTC сразу, не изобретаем своё                             |
