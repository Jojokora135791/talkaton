# 0003. Хранилище этапа 2 — SQLite вместо PostgreSQL

**Статус:** Принято · 2026-09-04 · заменяет выбор БД из шапки PLAN.md

## Контекст

На этапе 1 стенд собран на PostgreSQL в отдельном контейнере. К этапу 2 стало
видно, что весь профиль нагрузки — один разработчик, демо на ноутбуке и
приёмка в CI. Ни репликации, ни конкурентной записи, ни объёмов, ради которых
заводят сервер БД.

## Решение

Хранилище этапа 2 — **SQLite**, файл в docker-томе. Сервис `postgres` из
`docker-compose.yml` убран, миграции пересозданы под SQLite.

Провайдер задаётся одной строкой в `Program.cs` и строкой подключения
`ConnectionStrings:Sqlite`. Схема описана в EF Core и провайдеро-независима.

## Почему

- Стенд поднимается двумя контейнерами вместо трёх, джоба compose в CI —
  заметно быстрее.
- Демо переносится копированием одного файла базы.
- Обратный переход стоит замены `UseSqlite` на `UseNpgsql` и пересборки
  миграций: прикладной код о провайдере не знает.

Цена: теряем то, чего на этапе 2 всё равно нет — конкурентную запись
и серверные типы. Появится потребность на этапе 3 (VPS, несколько
пользователей одновременно) — вернём Postgres по той же схеме.

## Последствия

- `DateTime` в SQLite хранится как текст без `Kind`. Чтобы UTC не превращался
  в местное время на чтении, в `TalkatonDbContext` навешан конвертер сразу
  на все свойства `DateTime` и `DateTime?` — по договорённости из [0001](0001-utc-i-rrule.md).
- SQLite не создаёт каталог под файл базы, поэтому `DatabaseStartup`
  делает это сам: в compose файл лежит в примонтированном томе.
